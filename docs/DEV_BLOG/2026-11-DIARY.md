## 2026-11-18: Replay wide strings are UTF-16 on disk (retail replays no longer crash)

Opening any replay recorded by the Windows retail game (ZH 1.04) aborted the
macOS build with `__stack_chk_fail` in `RecorderClass::readReplayHeader`.

Root cause:
- the replay header stores its three wide strings (replay name, version,
  build time) and `ARGUMENTDATATYPE_WIDECHAR` command arguments as 16-bit
  code units, because `wchar_t` is 2 bytes on the original Windows build;
- on macOS/Linux `wchar_t` is 4 bytes, so `readWideChar()` consumed two
  UTF-16 units per character, the terminator was never found, every field
  after it was misaligned, and `readUnicodeString()` wrote `str[1024]` past
  its stack buffer (an off-by-one in the original loop).

What was done (`GeneralsMD/Code/GameEngine/Source/Common/Recorder.cpp`):
- replay wide strings and wide-char arguments are written and read as
  explicit `uint16_t` (UTF-16LE, BMP), matching the retail file format;
- `readUnicodeString()` is bounded and always terminates inside the buffer.

Validation (macOS arm64, headless `-replay`):
- all ten retail ZH 1.04 replays from the GeneralsXReplays history now parse,
  load their maps and simulate until the first CRC check (previously: abort
  on 8 of 10, early exit on 2).
- they then report `CRC Mismatch in Frame ~110`: the known, still open
  cross-architecture determinism gap (x87/MSVC vs clang/arm64 float results),
  not a parsing problem.

Compatibility note:
- replays written by earlier macOS/Linux builds of this lineage used 4-byte
  wide chars; they are now rejected cleanly (no crash) instead of loading.
  `GeneralsReplays/GeneralsXZH/Replays/macos_*.rep` are in that old format.

## 2026-11-19: First data mod via -mod, base game + Zero Hour launchers (macOS)

Goal: run the original game and a modded game side by side, for both the
base game and Zero Hour, without touching the original .big archives.

What was added:
- `scripts/mods/make_big.py`: packs a directory into a BIGF archive
  (format as read by `StdBIGFileSystem::openArchiveFile`).
- `mods/hello-generals`, `mods/hello-zh`: a mod that is a single INI file.
  It re-opens `ChinaVehicleDozer` and `ChinaTankBattleMaster` and only sets
  `BuildCost` / `BuildTime`. No game data is copied into it.
- `scripts/mods/install-macos-launchers.sh`: installs both game apps into
  `~/GeneralsX/Apps` plus one small launcher app per mod that starts the real
  app with `-mod <absolute path to .big>`.

Why a one-file mod works:
- `INI::loadDirectory` loads files in sorted order, so `zz_*.ini` comes last;
- in release builds a second `Object X` block for an existing object does not
  create a new one: `ThingFactory::parseObjectDefinition` parses the new fields
  into the existing template (the duplicate check is a `DEBUG_CRASH` only).

Validation (gui-sandbox VM, macOS arm64, Steam ZH data with `ZH_Generals/`):
- base game builds (`g_generals`) and runs: intro, shell map, skirmish as China;
- without the mod the China dozer costs 1000; with `-mod HelloMod-generals.big`
  it costs 123 and building one takes exactly 123 ($10000 -> $9877);
- same result in Zero Hour with `HelloMod-zh.big`;
- the launcher apps start the game with the mod using only the default paths
  (`~/GeneralsX/GeneralsZH`, `~/GeneralsX/Generals` -> `GeneralsZH/ZH_Generals`).

Notes:
- `-mod` was tested with a .big file only. For a directory, `parseMod` appends
  a backslash to the path; not tested on macOS.
- `build-macos-generals.sh` only finds a Vulkan SDK in `~/VulkanSDK`; building
  the `g_generals` target directly works with `VULKAN_SDK` set.

## 2026-11-20: Windows x64 builds, Steam data, big mods side by side

Windows x64 (MinGW-w64, SDL3/OpenAL/DXVK, preset `windows64-deploy` from the
GeneralsX `feat/windows-sdl3` branch) builds both games. Headless retail
replays (ZH 1.04, Generals 1.08) load Steam data and simulate until the known
`CRC Mismatch in Frame 110`.

Finding: the Steam / EA Zero Hour folder contains the whole base game in
`ZH_Generals/`. `loadBigFilesFromDirectory` scans the game folder recursively,
so base-game archives were loaded into Zero Hour; on Windows this broke
`Data\INI\Weapon.ini` (bisected to that folder). Fix without touching the
Steam install: run Zero Hour from a mirror folder made of links that leaves
`ZH_Generals/` out.

Big mods (Rise of the Reds, ShockWave, Contra, NProject, Zero Hour Reborn):
- `scripts/mods/make_mod_game_dir.py` builds one game folder per mod: real
  directories, links to the original files (symlinks on macOS, hard links on
  Windows), the mod's files linked on top; `*.gib` (GenLauncher's disabled
  archives) become `*.big`. `-mod` is not usable for these: it loads one
  archive or folder with inverted priority and skips loose files.
- `scripts/mods/install-windows-launchers.ps1`: one `.bat` per game / mod.
- `scripts/mods/install-macos-launchers.sh` (`ZH_SOURCE=...`): one app per mod,
  with `HOME` redirected to `~/GeneralsX/Profiles/<Mod>` so each mod has its
  own settings and saves. On Windows user data stays shared (Documents).

Validation (macOS arm64, headless retail ZH replay): every mod loads its own
INI set (RotR 577 INI files, ShockWave 760, Reborn 349, plain ZH 132) and
reaches the main menu; all but RotR then simulate the retail replay until the
CRC check (RotR stops right after opening it, expected for a replay recorded
without the mod). Same on Windows x64 (4 fewer INI files each: no
macOS-only SagePatch.ini).

Second finding: Zero Hour Reborn uses damage type names the engine does not
know (`HEAL`, `Surrender`) in `Armor.ini`. The original code stored them at
`m_damageCoefficient[-1]` (out of bounds, silently "worked"); the stricter
`scanIndexList` in the Windows branch threw and aborted the whole file.
`ArmorTemplate::parseArmorCoefficients` now skips unknown names in both games.

Mods are not part of this repository and are not redistributed.

## 2026-11-21: First unit tests find two compression bugs; replay tests

Unit tests (Catch2, `-DGENERALSX_BUILD_TESTS=ON`, `tests/`), set up like
sqlite_orm. The first test file only round-trips data through
`CompressionManager`, and found:
- `EAC/gimex.h` treated every `__APPLE__` target as big-endian (PowerPC
  Macs): RefPack, BTree and Huffman headers were byte-swapped on Intel/Apple
  Silicon Macs and iOS. RefPack is the preferred codec (maps, network map
  transfer), so data compressed on macOS was unreadable elsewhere.
- the pinned lzhl revision had `UINT32` = `unsigned long` (64-bit on
  macOS/Linux): LZHL compression wrote outside its hash table. Upstream had
  fixed it; the pin is bumped.

Replays:
- `scripts/replays/convert_wchar32_replay.py` converts replays recorded by old
  macOS/Linux builds (4-byte wide chars) to the retail layout.
- The three `GeneralsReplays/GeneralsXZH/Replays/macos_*.rep` (May 2026)
  convert cleanly but go out of sync after ~1 minute of game time (CRC
  mismatch at frames 1200-1900). The same happens with the old 4-byte reader
  on the unconverted files, so the conversion is exact and the game logic
  changed since they were recorded. New recordings are needed.
- `scripts/qa/replays/run-replay-tests-macos.sh`: one command, throwaway
  profile, logs in `logs/replay-tests/`. Default replay set:
  `tests/replays/macos/` (to be recorded).

## 2026-11-22: The May replays desynced because of name keys, not logic

Correction to the entry above: the game logic did not change. A build of the
May commit (8fdc93f4c) plays all three May replays to the end, and `git
bisect` led to the June ExtrasMenu commits, which contain no game logic.

Cause, found with a temporary per-object CRC probe: at frame 1169 the GLA
barracks lacked the `Upgrade_GLACamoNetting` bit. `MSG_QUEUE_UPGRADE` carries
the upgrade's name key, and name keys are handed out in order of first use.
The five `ExtrasMenu*` callbacks were keyed in `FunctionLexicon::init`, before
the INI data, so every upgrade key moved by 5 and the replay queued a
different upgrade. The same would desync games between builds.

Fix: GeneralsX-only callbacks go into separate tables keyed by
`FunctionLexicon::loadLateTables()` at the end of `GameEngine::init`. Only
names registered during init must match other builds; later names already
depend on which menus a player opened, even in the original game.

The replay runner now plays the `GeneralsReplays` macOS replays (converting
them on the fly); all three pass on main. Rule: never add a name that
becomes a name key (`nameToKey`, `NAMEKEY`) to engine init before the game
data is loaded.
